# Aperture v0.7.10 Release Notes

This release fixes database restores. Restoring from the admin panel appeared to finish in seconds while it was actually still running, and backups created by earlier releases could not be restored at all. **Baseline:** follows **v0.7.9**.

**No migration, no configuration change, no action required.** Pull and restart as usual.

---

## At a glance

| Theme | What shipped |
| --- | --- |
| **Restore progress** | A restore no longer appears to finish instantly. Progress keeps reporting for the whole operation, even though the restore signs you out partway through. |
| **Restoring old backups** | The bundled `pg_restore` is now PostgreSQL **17**, so every backup Aperture has ever written can be restored. v0.7.9's pinned-16 client could not read them. |
| **Skip the safety backup** | The automatic pre-restore backup is now optional and visible. On a large database it roughly doubled the wait, invisibly. |
| **CI fix** | Release tags now actually build and publish images. Tag pushes were silently publishing nothing. |
| **Database unchanged** | Still `pgvector/pgvector:pg16`. Nothing to migrate. |

---

## Summary for users

If you have ever started a restore and watched it claim success in a few seconds — then found you could not log back in — that was this bug. **The restore was working the entire time.** Nothing told you.

Restoring now shows the current step and elapsed time for the whole operation, warns you up front that it signs you out, and gives you a button back to the login screen when it finishes.

---

## Summary for admins

### Why a restore looked instant

Sessions are stored in the database. A restore runs `pg_restore --clean`, which drops and recreates every table — including `sessions` — so the admin who started the restore loses their own session a few seconds in.

The progress endpoint required that session. Once it was gone, polling returned 401, and the UI treated 401 as "the job finished": it cleared the progress panel and reported success. Meanwhile the restore continued in the background, sometimes for many minutes on a multi-gigabyte database, with nothing on screen and no way to log in until it completed.

**The restore was never broken. The reporting was.**

### The fix

Starting a restore now returns a short-lived token, HMAC-signed with `SESSION_SECRET` and scoped to that single job. The progress endpoint accepts an admin session **or** that token, and verifying a token touches no database — so progress keeps reporting through exactly the window where the session no longer exists.

Alongside that:

- **Elapsed time and current step** are shown throughout. `pg_restore` reports no percentage, so nothing pretends to be one.
- **An explicit warning before you start**, saying the restore will sign you out.
- **A "Go to login" button** when it finishes, instead of a page where every request now fails.
- **The pre-restore safety backup is now a checkbox.** It still defaults to on, but it was silently doubling the wait on large databases and never appeared in the UI.

### Restoring backups from earlier releases

v0.7.9 pinned the bundled client to PostgreSQL 16 so it matched the bundled server. That fixed restoring **new** backups with the tools inside the database container, but broke restoring **old** ones.

Releases before v0.7.9 shipped an unpinned client that had drifted to PostgreSQL 17, then 18, and those write archives with header version 1.16. A pinned-16 `pg_restore` refuses them:

```
pg_restore: error: unsupported version (1.16) in file header
```

The client is now pinned to **17**, which reads archives from every earlier version.

| Pairing | Backups | Restore pre-0.7.9 backups |
| --- | --- | --- |
| client 16, server 16 (v0.7.9) | works | **fails** |
| client 17, server 16 (this release) | works | works |
| client 16, server 17 | **fails entirely** | — |

One narrow limitation remains: on the shipped PostgreSQL 16 server, the `.dump` files Aperture writes are archive 1.16, so the tools *inside* the `aperture-db` container cannot read them. This never affects restoring through Aperture. For manual restores, use a 17 client — see [Backup & Restore](../admin/backup-restore.md#restore-fails).

The remaining rule: **do not run a PostgreSQL server newer than 17**, or `pg_dump` refuses to run and backups stop. Aperture logs an explicit error at startup if it detects that.

### Release tags now build

Tag pushes matched the `v*` trigger, passed validation, then skipped every Docker job, so no versioned image was ever published. The jobs were gated on a path filter, and `dorny/paths-filter` cannot compute a diff for a tag — the tag points at a commit that already exists, so it reports no changed paths. Tag pushes now bypass that filter.

Versioned images `0.7.7`, `0.7.8`, and `0.7.9` have been published retroactively.

## Database migrations

No new database migrations are included in v0.7.10.

The bundled database image is unchanged at `pgvector/pgvector:pg16`. Nothing about your data directory changes.

## API notes (operators)

- **`GET /health`** — **`version`** now reports **0.7.10**.
- **`POST /api/backup/restore`** now returns a `progressToken` alongside `jobId` in async mode.
- **`GET /api/jobs/progress/:jobId`** accepts an optional `token` query parameter as an alternative to session auth. A token is valid for one job ID, expires after six hours, and authorizes reading that job's progress and nothing else.
- No route URLs, methods, or existing response shapes changed.
- The startup log reports the database server and client majors; client 17 against server 16 is expected for this release.

## Update instructions

### For Docker users

```bash
docker compose pull
docker compose up -d
```

No migration step, and no compose changes.

### Operator checklist

1. Confirm the app reports **v0.7.10** in the left rail / setup wizard and `/health`.
2. Confirm the database client line in the startup logs:
   ```bash
   docker logs aperture | grep -i "client"
   ```
   Client 17 against server 16 is correct for this release.
3. Run a manual backup from **Admin → Settings → System** and confirm it completes.
4. If you have a backup from before v0.7.9, confirm it is now restorable from that same screen. That is the defect this release fixes.
5. When you next run a restore, expect to be signed out when it completes. That is by design — the restore replaces the session data — and the UI now tells you so and offers a way back in.

---

## Optional: PostgreSQL 17

Running PostgreSQL 17 is supported but **not required or recommended**. PostgreSQL 16 receives fixes until November 2028, and the shipped configuration is the tested one.

If you want to move anyway, `scripts/migrate-db-pg17.sh` performs the upgrade with verification before anything destructive, and [PostgreSQL 16 and 17](../admin/postgres-17-migration.md) documents the manual procedure, the bind-mount case, and a verified path back down to 16.
