# Aperture v0.7.9 Release Notes

This release is a **maintenance and reliability release** focused on database backup integrity. It fixes a defect that made backups unrestorable with the tools shipped alongside them, and adds the tooling for an upcoming PostgreSQL 17 upgrade. **Baseline:** follows **v0.7.8**.

---

## At a glance

| Theme | What shipped |
| --- | --- |
| **Backup integrity** | Pinned the bundled `pg_dump` / `pg_restore` to PostgreSQL 16 so backups match the database Aperture ships with. Previously the client version drifted with the base image and had reached 18. |
| **Startup diagnostics** | Aperture now logs its database server version and backup client version at startup, and warns explicitly when they are incompatible. |
| **PostgreSQL 17 preparation** | New migration script and guide. The bundled database still runs PostgreSQL 16 in this release. |
| **Documentation** | Corrected the documented backup format, added manual restore instructions, and added a troubleshooting section covering the real error messages. |

---

## Summary for users

Nothing changes in the interface, and no action is required.

Behind the scenes, database backups are now guaranteed to be restorable by the tools that
ship with Aperture. If you previously downloaded a backup and could not restore it manually,
the [Backup & Restore](../admin/backup-restore.md) guide now explains exactly why and what to
do about it.

## Summary for admins

### The backup client defect

Aperture's Docker image installed Alpine's `postgresql-client` package without pinning a
major version. That package follows Alpine's current default, which had advanced to
PostgreSQL **18**, while the bundled database runs PostgreSQL **16**.

`pg_dump` 17 and later write custom-format archives with header version 1.16, which
`pg_restore` 16 cannot read:

```
pg_restore: error: unsupported version (1.16) in file header
```

Aperture's own restore was unaffected, because it uses the client inside the app container,
which matched whatever wrote the backup. The failure appeared in every other path: restoring
inside the database container, recovering onto a new host, or restoring while the app is
stopped. Nothing in the build pinned or checked the version, so it changed without any commit
touching it.

The client is now pinned to `postgresql16-client` to match `pgvector/pgvector:pg16`.

**Backups created before this release are still valid.** They were written by a newer client,
so they need a `pg_restore` of version 17 or newer. The troubleshooting guide gives a one-line
command for this.

### New startup check

On boot, Aperture compares its bundled backup client against the live database and logs the
result:

- **Matched** — logged at info level.
- **Client older than server** — logged as an error. `pg_dump` refuses to run against a newer
  server, so backups would fail silently. This is the condition to watch for.
- **Client newer than server** — logged as a warning, noting that the resulting backups need a
  matching or newer `pg_restore`.

The check never blocks startup and never throws.

### PostgreSQL 17 preparation

A future release will move the bundled database to PostgreSQL 17. **This release does not.**
The tooling ships now so you can migrate on your own schedule:

- `scripts/migrate-db-pg17.sh` — performs the migration in a safe order, verifying the export
  is readable before removing anything, and comparing row counts afterward.
- [PostgreSQL 17 Migration](../admin/postgres-17-migration.md) — scripted and manual
  procedures, rollback, bind-mount handling, and troubleshooting.

Two things worth knowing before that release lands:

1. **Your existing backups will work on PostgreSQL 17.** `pg_restore` reads archives from
   older versions of `pg_dump`. No conversion tooling is needed.
2. **A major version change requires a new data directory.** PostgreSQL refuses to start on a
   data directory from a different major version, so the upgrade is an export/import rather
   than an in-place change. Your data is not damaged if you change the image without
   migrating — the container exits before writing anything.

## Update instructions

### For Docker users

```bash
docker compose pull
docker compose up -d
```

No migration step is required for this release.

### Operator checklist

1. Confirm the app reports **v0.7.9** in the left rail / setup wizard and `/health`.
2. Check the startup logs for the database client line:
   ```bash
   docker logs aperture | grep -i "client"
   ```
   You want the matched message. An error about the client being older than the server means
   backups are failing.
3. Run a manual backup from **Admin → Settings → System** and confirm it completes.
4. Optional but recommended: verify the new backup restores with the database container's own
   tools, which now works:
   ```bash
   docker exec -i aperture-db pg_restore --list < /path/to/backup.dump > /dev/null && echo OK
   ```
5. If you plan to move to PostgreSQL 17 early, read
   [PostgreSQL 17 Migration](../admin/postgres-17-migration.md) first.
