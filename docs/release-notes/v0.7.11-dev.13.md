# v0.7.11-dev.13 — LAN and reverse-proxy access

Changes since dev.12:

- Aperture can load at a direct LAN address and its public reverse-proxy address while `APP_BASE_URL` remains set to the public URL. Same-origin requests from the LAN page, including JavaScript modules, no longer fail the production CORS check.
- Session cookies now support direct HTTP on a separate LAN hostname/IP while retaining Secure cookies for the configured HTTPS public hostname. Sign in separately at each address; both sessions use the same account and saved settings. Logging out at one address leaves the other session alone.
- Untrusted browser origins receive HTTP 403 (`CORS_ORIGIN_DENIED`) before route handlers execute, rather than an internal server error. Other LAN hosts/ports are not automatically granted cross-origin access, and spoofed forwarding headers cannot authorize a rejected origin.
- Added LAN/reverse-proxy documentation, focused origin and authentication regression tests, and a corresponding CI check.

No new settings, database migrations or admin/user preference changes are required. Keep the public `APP_BASE_URL` and existing OAuth callback configuration. For direct HTTP, use a LAN IP or separate LAN hostname; cookies share scope across ports on the same hostname, so the HTTPS public hostname retains Secure cookies even on another port.

Use `ghcr.io/dgruhin-hrizn/aperture:dev` for this development release, or pin `:0.7.11-dev.13`. `:latest` remains the stable channel.

Validation: lint, all workspace type checks, production build, five browser-access/auth integration tests and the existing Upcoming Episodes (20), UI performance (27), Discovery (20) and appearance (7) regression tests. The built-server smoke test confirms HTML/modules return 200 for LAN and public origins, preflight returns 204, unauthenticated protected reads remain 401 and untrusted login requests return 403.

See [LAN and reverse-proxy access](../lan-reverse-proxy-access.md) for session scope, proxy headers, OAuth behavior and verification.
